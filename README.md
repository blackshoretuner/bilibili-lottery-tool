# B 站抽奖 + 关注管理

两个配套工具，共用一份 `config.json`：

- **抽奖**（`main.py`）：自动找到 B 站上的**转发抽奖**动态，完成参与所需的「关注 + 转发 + 评论」，并记住参与过哪些，不会重复刷。
- **关注管理**（`follow.py`）：把关注按群体分类，方便**整组取关**；顺带清理已注销和长期不更新的号。参与抽奖久了关注会膨胀，这个用来收拾。

> ⚠️ **先读这段**：B 站原来有个接口能准确回答「这条动态是不是官方互动抽奖、什么时候开奖」，**这个接口已经下线了**。所以现在改成两步猜：
> - **是不是抽奖** → 看正文关键词，会有误判
> - **还开不开着** → 从正文里解析「开奖时间：X月X日」，正文没写才退回看「发布多久了」
>
> 默认配置偏保守，宁可漏掉也别乱转。实测扫 482 条动态：筛出 29 个抽奖，挡掉 8 个已开奖的、2 个太老的，剩 19 个都是还开着的真转发抽奖。
>
> **每次改完关键词一定要先 `--test`，自己看一眼正文摘要对不对。**

**最省事的用法：双击 `一键运行.bat`，选 `9` 打开网页版。**

网页版比命令行强在**能逐条勾选** —— 扫出来的抽奖挑想参与的，关注挑想取关的，不用整类一刀切。用 Python 标准库起的本地服务，**没有新增依赖**，只监听 `127.0.0.1`，局域网里其他设备访问不到。

一共五个文件：

| 文件 | 干什么 |
| --- | --- |
| `一键运行.bat` | 双击它，出菜单，选数字。**推荐用这个** |
| `config.json` | 你的设置（**需要你自己创建**，下面第 3 步说怎么弄） |
| `web.py` | 网页版界面 |
| `main.py` | 参与抽奖 |
| `follow.py` | 管理关注。Cookie、限速、风控那套逻辑是从 `main.py` 复用的 |

### 网页版长什么样

两个选项卡：

- **参与抽奖** — 点「开始扫描」出一张表，每行是命中的关键词、发布/开奖时间、正文摘要。勾掉误判的，再点「参与勾选的」。跑完弹出每条的结果，包括**评论验证结论**。
- **管理关注** — 一排类别按钮（`游戏区` `游戏区/单机游戏` `已注销` `内容:原神`…都带人数），点一个出名单表格，逐个勾选后取关。

底下有实时日志，跑到哪一步一眼看到。**取关的复选框默认不勾**（不可逆操作要你逐个确认），抽奖的默认勾上。

命令行启动：

```bash
python web.py
```

不想自动开浏览器加 `--no-open`，换端口加 `--port 8800`。

## 从零开始，五步搞定

### 第 1 步：装 Python

在命令行里输入下面这行，看看电脑上有没有装：

```bash
python --version
```

看到 `Python 3.9` 或更高的版本号就行。如果提示"找不到命令"，去 [python.org](https://www.python.org/downloads/) 下载安装，**安装时记得勾上 "Add Python to PATH"** 这个选项（很关键，不勾后面命令会用不了）。

> **怎么打开命令行？** Windows 按 `Win + R`，输入 `powershell` 回车。

### 第 2 步：装脚本要用的东西

先用 `cd` 命令进到脚本所在的文件夹：

```bash
cd "C:\Claudcode\bilibili lottery"
```

然后装依赖（只有一个库，几秒钟）：

```bash
pip install -r requirements.txt
```

### 第 3 步：拿到你的 Cookie（新手最容易卡住的一步，慢慢来）

Cookie 是你的登录凭证，脚本靠它证明"我就是你"，才能替你转发和评论。

1. 用 Chrome 或 Edge 打开 [bilibili.com](https://www.bilibili.com)，**确认自己是登录状态**。
2. 按 `F12` 打开开发者工具，点上方的 **Network（网络）** 标签。
3. 按 `F5` 刷新页面，下面会刷出一大堆请求。
4. **随便点一条**请求，右侧会出现详情面板。
5. 在右侧找到 **Request Headers（请求标头）** 这一段，往下翻，找到以 `cookie:` 开头的那一行。
6. 把 `cookie:` **后面**那一长串全部选中复制（很长，可能有好几百个字符，都要）。

拿到之后：

1. 把文件夹里的 `config.example.json` **复制一份**。
2. 把复制出来的那份**改名成 `config.json`**。
3. 用记事本打开它，把第一行 `"cookie": "..."` 引号里的占位文字**整段替换**成你刚复制的内容。

改完应该长这样（`...` 处是你自己那一长串）：

```json
{
  "cookie": "buvid3=XXXX; SESSDATA=YYYY; bili_jct=ZZZZ; DedeUserID=123456; ...",
  ...
}
```

> **自查**：粘贴进去的那串里，应该能搜到 `SESSDATA` 和 `bili_jct` 这两个词。搜不到就是复制错了（大概率复制的是 Response Headers 而不是 Request Headers）。
>
> ⚠️ **Cookie 等于你的账号密码**。别发给任何人、别上传到网上。脚本已经设置好不会把 `config.json` 提交到 git。

### 第 4 步：先试跑一次（不会真的操作）

双击 `一键运行.bat`，选 **1**。或者用命令行：

```bash
python main.py --test
```

加了 `--test` 就是**只看不动手**：它会去找抽奖、列出找到了哪些、每条命中了什么关键词、正文写的是什么，但**一个都不会真的参与**。

正常输出长这样：

```

关注流: 241 条动态

============================================================

  · https://t.bilibili.com/1241199107127640067  ASUS华硕官方UP  08-27发布 / 09-14开奖  [命中 抽奖+转发]
      ​ROG 20寸行李箱，秒变移动展柜？带痛层的RO宝行李箱你心动了吗？快来和RO…
  · https://t.bilibili.com/1242058736219979794  一只小钻  08-30发布 / 09-10开奖  [命中 抽奖+转发]
      🎁 参与方法：关注 @一只小钻 ​转发＋评论本动态 = 参与成功，一定要关注哦～…

```

每条都会标出 **命中了哪些关键词**、**发布时间** 和 **解析出的开奖时间**，方便你一眼看出准不准。

**这一步绝对不能跳过。** 因为判定是靠关键词猜的，你必须自己看一眼那个「正文摘要」——确认列出来的真是转发抽奖，而不是误判。同时它也顺便验证了 Cookie 对不对、网络通不通。

### 第 5 步：正式跑

双击 `一键运行.bat`，选 **2**。或者用命令行：

```bash
python main.py
```

它会先把要参与的抽奖列出来，问你一句，**输入 `y` 回车**才会真的开始。

跑起来之后会比较慢——每个动作之间会随机等 20~45 秒。**这是故意的**，为了不被 B 站判定成机器人。参与 10 个抽奖大概要十几分钟，让它自己跑就行。

## 配置项说明

打开 `config.json` 可以改这些。**不确定的就别动，默认值是稳妥的。**

### 去哪里找抽奖

| 配置项 | 意思 |
| --- | --- |
| `up_mids` | 盯几个 UP 主，填 uid 数字。**已预置两个抽奖聚合号**——他们天天转发抽奖，脚本会从他们的转发里挖出原始抽奖动态。这是出货最多的来源 |
| `topic_ids` | 抽奖话题板块，填数字 id。已预置两个实测有效的（`#抽奖！！！#` 有 2400 万浏览）。每个话题的**热门和最新两个 tab 都会扫**，两边内容几乎不重叠：热门那边是大额长周期抽奖，最新那边是刚发的 |
| `learn_topics` | 自动学习话题。扫到带 `#…抽奖…#` 标记的动态时，把话题 id 记进 `record.json`，下次连整个话题一起扫，跑得越久覆盖越广 |
| `dynamic_ids` | 手动指定某几条动态。可以直接填链接，比如 `["https://t.bilibili.com/123456"]` |
| `scan_following` | 要不要顺便扫你自己的关注动态流。`true` = 要 |
| `feed_pages` | 关注流翻几页，默认 10（每页约 25 条）。**这是产量最大的来源**——你关注的人越多越管用 |
| `up_pages` | 每个 UP 空间翻几页，默认 3 |

> **话题页为什么没有翻页配置？** 实测它封顶就 20~22 条：`page_size` 调到 100 也只返回 22 条，`offset` 直接是空的，翻不动。所以话题这条路已经榨干了，想要更多只能靠关注流和 UP 空间。

> **自己加话题 id 怎么找？** 在 B 站找一条带 `#互动抽奖#` 之类标签的动态，点那个蓝色标签，地址栏会变成 `https://www.bilibili.com/v/topic/detail/?topic_id=12345`，把那串数字填进 `topic_ids` 就行。
>
> （B 站按名字搜话题的接口已经下线了，所以只能填数字 id，没法直接写话题名。）

> **自己加 UP 怎么找？** 打开 UP 主空间页，地址栏 `https://space.bilibili.com/123456` 里的数字就是 uid。

### 怎么判断是不是抽奖

| 配置项 | 意思 |
| --- | --- |
| `lottery_words` | 抽奖词。正文里至少要命中一个，比如「抽奖」「包邮送」 |
| `action_words` | 动作词。默认只有「转发」——转发抽奖就是靠转发参与的。**加上「评论」「关注」会把评论区抽奖也误判进来** |
| `skip_words` | 排除词。命中任意一个就跳过。默认已包含：已开奖、中奖名单、评论区抽、抽奖合集、传送门等 |

改完这三组词后，**务必先 `python main.py --test`**，看一眼「命中」了什么、正文摘要对不对。

### 参与时做什么

| 配置项 | 意思 |
| --- | --- |
| `do_follow` | 是否关注 UP。**大部分抽奖要求关注，建议保持 `true`** |
| `follow_at_mentions` | 联名抽奖常写「关注 @甲 和 @乙」，打开后会把正文 @ 到的号一起关注。**关掉的话联名抽奖等于没参与** |
| `do_repost` | 是否转发。**转发抽奖的核心，必须 `true`** |
| `do_comment` | 是否评论。有些抽奖要求评论。不想刷评论可以改成 `false` |
| `follow_group` | 关注的 UP 会被丢进这个分组，以后想批量取关很方便。不想分组就填 `""` |
| `repost_texts` | 转发时说的话。脚本每次随机挑一句，避免每条都一样 |
| `comment_texts` | 评论时说的话。同上 |

### 参与多少 / 多快

| 配置项 | 意思 |
| --- | --- |
| `max_age_days` | **兜底用**：正文里没写开奖时间时，只参与最近 N 天发布的。默认 21。正文写了开奖时间的不受它影响。填 `0` 不限 |
| `max_per_run` | 跑一次最多参与几个。**你的 config.json 里现在是 3**（保守起步用），模板默认 20 |
| `max_per_day` | 一天最多参与几个。默认 40 |
| `min_delay` / `max_delay` | 每个动作之间随机等几秒。默认 20~45。**不建议调到 10 以下，容易被封** |

> 先用 `max_per_run: 3` 小规模跑一两天，观察账号没事再往上调。

## 出问题了怎么办

脚本的报错都是中文人话，先看提示。下面是几种常见情况：

| 你看到的 | 什么意思 / 怎么办 |
| --- | --- |
| `× 找不到配置文件` | 第 3 步没做完，`config.json` 还没创建 |
| `× 不是合法的 JSON` | `config.json` 编辑坏了。常见原因：少了逗号、多了逗号、引号打成了中文的 `“”` |
| `× config.json 里的 cookie 没填对` | Cookie 复制错了，回第 3 步重来。注意要 **Request** Headers 里的 |
| `Cookie 已失效` / `账号未登录` | Cookie 过期了（改密码、退登录都会导致），重新复制一份 |
| `cookie 少了这些字段` | 复制得不全，或者中间被截断了。整条重新复制一次 |
| `被 B 站拦截（412）` | 跑太猛了。等几个小时再跑，并把 `min_delay` / `max_delay` 调大 |
| `撞到风控了，歇 600 秒` | 正常的自我保护，让它等着就行。连续撞两次会自动收工 |
| `这轮没找到新的可参与抽奖` | 不是报错。可能都参与过了，或者关键词太严。可以往 `up_mids` 里多加几个爱办抽奖的 UP |
| `接口可能已下线` | B 站改接口了。单个来源失效不影响其他来源，脚本会跳过继续跑 |
| `关注失败，已达关注上限` | 关注数满了（普通 1000 / 大会员 2000 / 6 级 5000）。抽奖都要求关注，脚本会**直接停机**。用 `follow.py` 取关一批再来 |
| `pip 不是内部或外部命令` | 第 1 步装 Python 时没勾 "Add Python to PATH"，重装一次并勾上 |
| bat 窗口一闪就没了 | 不会的，bat 里已经加了停留。如果真发生，说明 bat 文件被改坏了 |
| 输出里有 `?` 问号 | 正常。抽奖正文里的 emoji 在非 UTF-8 控制台显示不出来，不影响功能 |

想看更详细的信息，加 `-v` 重跑；完整日志在 `logs/run.log` 里。

## 几个要知道的事

**判定是靠猜的，不是靠官方接口。** 官方判定接口已下线（见开头的警告），现在靠正文关键词。默认规则是：正文里要同时出现「抽奖词」（抽奖、包邮送…）和「转发」，且不含排除词（已开奖、评论区抽、抽奖合集…）。

**评论区抽奖会被排除。** 那种"评论区抽一位"的抽奖，你转发一百遍也没用，所以默认关键词里 `action_words` 只留了「转发」。

**怎么判断抽奖还开不开着。** 分两步：

1. **先从正文里解析开奖时间**。抽奖正文基本都会写「开奖时间：2026年10月5日」「直播开奖日期：8月8日18:00」这类话。支持 `2026年10月5日` / `2026.4.30` / `2026.01.31-2026.02.28` / `8月30日` 等写法；同时出现多个日期时取最晚那个（开奖总比活动开始晚）。解析出的时间已经过了就跳过。
2. **正文没写时间**，才退回看 `max_age_days`（默认只要 21 天内发布的）。

这个顺序很关键。实测遇到一条 iPhone 抽奖：发布于 7 月 29 日、开奖在 10 月 5 日，**还开着**——但只看发布时间会被 21 天规则误杀。现在能正确留下。

**评论是发完回读验证的，不只看接口返回。** 很多抽奖要求「关注+转发+评论」三样都做到才算参与，所以光看接口返回 code 0 不够。脚本的做法是：

1. **先定位评论区**。评论区并不挂在动态自己身上——图文动态的评论区是 `oid=379837513 type=11` 这种，跟动态 id 毫无关系。正确的值在动态详情的 `basic` 里，而话题卡片这些列表接口经常不返回它，所以缺了就回头查一次详情。**查不到就跳过评论，不往错地方发。**
2. **发完拿 rpid**，再用 `reply/reply?root=<rpid>` 按 rpid 查一遍。评论不存在会明确返回 `12006`，所以这是确定性的检查，隔多久都能复查。
   （一开始我写的是翻评论列表找 rpid，实测发现那样只在「刚发完」那一刻有效——热门抽奖评论区一天几千条，有一条 18677 条的，隔天复查全是假警报。）

报告里会直接写结论，`record.json` 里也会存 `rpid` 和验证结果，随时可以翻账：

```
  ✓ [关转评] https://t.bilibili.com/xxx  某某UP  10-05开奖  [抽奖+转发]
        评论验证: 已确认（在评论区找到了）  rpid=88886666
```

四种结论的含义：

| 结论 | 意思 |
| --- | --- |
| `已确认（按 rpid 查到，作者是本账号）` | 稳了 |
| `没找到（这条评论不存在…）` | **接口说成功但评论查不到**，多半被删或没过审，值得自己去看一眼 |
| `存疑（rpid 查到了，但作者不是本账号）` | 不该发生，出现了说明有 bug，别当成功 |
| `无法验证：…` | 查询本身失败了。跟「没找到」区分开——不代表评论没发出去 |

**发完会等几秒再查。** B 站对刚发出去的评论有索引延迟，发完立刻查会误报「没找到」——实测一次跑 3 条误报了 2 条，隔两分钟再查全都在。所以现在最多重试 4 次、间隔逐次加长，实在查不到才报「没找到」。

假警报比不验证还糟：会让你以为评论丢了，跑去手动补一条，结果变成重复评论。

**不会转发自己的转发。** 我们的转发文案本身含「转发抽奖」字样，不做处理的话，上一轮自己发的转发会被当成新抽奖再转一遍。现在会跳过自己发的动态。

**同一个抽奖只参与一次，哪怕它有好几个入口。** 一个抽奖经常同时以两种形式被扫到：原动态，以及别人转发它的那条。两条都参与的话，B 站会把你的两次转发都挂到同一个根动态上，等于同一个抽奖转了两次（真发生过）。所以：

- 扫描后按根动态**折叠重复入口**，只留一条（留原动态那条，并继承被折叠那条的 @ 名单，免得漏关联名方）
- **每次动手前再当场确认一次**——扫描那一刻的快照不够用，参与完 A 之后 B 站可能把转发挂到了 A 的根动态上，名单里若还有那条根动态，不当场记下就会再转一遍

**不会重复参与，而且不只靠本地记录。** 每次开跑前会先读一遍**你在 B站 上的实际转发历史**，和 `record.json` 一起用来去重。这么做是因为本地记录有两个洞：

1. 它可能被删或记漏，**你手动转发过的抽奖它根本不知道**
2. 转发「转发动态」时，B站 会把你的转发挂到**根动态**上。记录里存的 id 和实际转到的 id 对不上，下次扫到那条根动态就会再转一遍

实测：B站 上有 12 条转发、`record.json` 只记了 8 条；改完后单轮跳过数从 4 涨到 12，也就是有 8 个抽奖本来会被重复转发。

现在参与成功时会把根动态 id 也一并记下（标成 `alias_of`，不占每日额度）。不想读转发历史可以把 `check_my_reposts` 关掉，那就退回只信本地记录。

**关注会越来越多。** 参与抽奖必须关注 UP，跑久了关注列表会膨胀。所以脚本默认把它们都丢进「抽奖」分组，你随时可以去关注列表里按分组批量取关。

**开奖了脚本不会通知你。** 中奖是 B 站发私信通知的，记得偶尔看一眼消息。

**账号风险自己评估。** 自动化批量互动可能不符合 B 站用户协议。默认配置已经尽量保守（随机间隔、每日上限、撞风控自动停），但风险不等于零。建议先小规模试，别用主号猛刷。

## ⚠️ 关注数有上限，满了整个工具就废一半

B 站的关注上限：**普通用户 1000 / 大会员 2000 / 硬核会员（6 级）5000**。

抽奖基本都要求关注，**关注满了之后，参与新 UP 的抽奖 = 白转白评论**。这不是理论问题，这个账号就撞上了：

```
关注 西昊人体工学椅 失败: [22009] 关注失败，已达关注上限
当前关注数: 5000 / 5000
```

所以做了两道防线：

- **参与时撞到就停机**，不再只记一行日志继续刷。停下来时会告诉你怎么腾位置
- **自检里单列「关注余量」**，剩余不足 50 个就提醒

```
【关注余量】
  已满  5000/5000，关不了新号了
        抽奖基本都要求关注，这种状态下参与等于白转。
        腾位置：python follow.py --unfollow 已注销
```

腾位置就是下面这个工具的活。

## 关注管理（follow.py）

参与抽奖必须关注 UP，跑久了关注列表会膨胀（**实测这个号已经 4994 个关注**）。这个工具用来按群体收拾。

### 先看分类报告

```bash

```

第一次会抓一遍完整关注列表（4994 个约三分钟，之后走缓存 `follows.json`）。输出长这样：

```

  抽奖               6 人
  未分组           4988 人
  互关              93 人
  单向关注          4901 人

```

### 类别

**账号属性类**（不用额外请求，抓完关注列表就有）：

| 类别 | 依据 |
| --- | --- |
| `抽奖` | `record.json` 里参与过的 uid，或在「抽奖」分组里 |
| `未分组` | 没归进任何关注分组 |
| `互关` / `单向关注` | 对方有没有回关 |
| `特别关注` | 是不是特别关注 |
| `机构号` / `个人认证` / `无认证` | B 站的认证类型 |
| `关注超一年` / `最近30天关注` | 关注时间 |

**内容分区类**（要深度检查）：

| 类别 | 例子 |
| --- | --- |
| 一级分区 | `游戏区` `动画区` `科技区` `生活区` `时尚区` `知识区` `音乐区` `影视区`… |
| 二级分区 | `游戏区/单机游戏` `游戏区/电子竞技` `游戏区/手机游戏` `动画区/MAD·AMV` `科技区/数码` |
| `二创` | 鬼畜、MAD·AMV、音MAD、人力VOCALOID、影视剪辑、粉丝创作等归并成一类 |
| `内容:xxx` | 从最近投稿标题里认的，比如 `内容:原神` `内容:艾尔登法环` `内容:显卡` |
| `分区未知` | 查过了但没有投稿，或分区取不到 |

**类别名不是我写死的清单，是按你关注的实际情况生成的** —— 你没关注美食区 UP，就不会出现「美食区」这个类别。

**账号状态类**（要深度检查）：

| 类别 | 依据 |
| --- | --- |
| `已注销` | 账号查不到，或被封禁 |
| `长期不更新` | 最后一条动态超过一年 |

### 分区是怎么认出来的

B 站的投稿分区分两级，但接口只给一半信息：

- **一级分区名**：`arc/search` 的 `tlist` 里有，权威
- **二级分区**：只给 `typeid` 数字，**不给名字**。`view` 接口的 `tname` 现在返回空字符串，官方也没有分区树接口

所以二级分区靠内置的 116 条 `typeid → 分区名` 对照表。**表里没有的 typeid 会显示成 `动画区/未知(257)`**，不会瞎猜成某个分区。

一级分区也跟着 `typeid` 走（而不是直接用 `tlist` 的历史统计），否则会出现「鬼畜区/电子竞技」这种自相矛盾的标签 —— 那是历史投稿以鬼畜为主、但最近改做电竞了。以最近投稿为准更有参考价值。

「具体在做什么」是从最近 8 条投稿标题里匹配词库得来的，**仅供参考**。B 站没有「这个 UP 在做哪个游戏」的接口，标题匹配是唯一可行的办法。想加词就在 `config.json` 里写：

```json
"content_words": ["某个游戏名", "某个番名"]
```

> 顺便说一句：实测名字或签名里带「抽奖」的**一个都没有**，所以抽奖号只能靠参与记录和分组认，关键词那条路走不通。

### 深度检查（找注销号和僵尸号）

```bash
python follow.py --deep 200
```

账号状态和内容分区都要逐个查，每个 UP 三次请求（账号信息 + 动态 + 投稿列表）。4994 个全查完约一万五千次请求，一次跑完必被限流，**所以是增量的**：每次查一批，查过的记在缓存里，下次自动跳过，撞限流就存盘收工不丢进度。查 200 个大约 8 分钟。

### 按类取关

**先演练**，看清名单再动手：

```bash
python follow.py --unfollow 已注销 --dry-run
```

确认没问题再真取关，可以限制数量：

```bash
python follow.py --unfollow 已注销 --limit 50
```

类别名带斜杠或冒号的记得加引号：

```bash
python follow.py --unfollow "游戏区/手机游戏" --dry-run
python follow.py --unfollow "内容:原神" --dry-run
```

几个安全设计：

- **默认要输完整的 `yes`** 才继续，不是随便按个 y
- 名单里有互关的会**单独警告**（取关会断掉互关关系）
- 取关之间用 `config.json` 里的 `min_delay`/`max_delay` 间隔，撞风控**立刻停**
- 取关成功的会从缓存移除，进度实时存盘
- **取关不可逆**：重新关注会丢掉原来的关注时间，分组也要重新分

## 脚本是怎么工作的

```
第 1 步  从四个入口捞动态
        抽奖话题板块【热门+最新两个 tab】/ 指定 UP 空间 / 你的关注流 / 手填链接
           ↓  按动态 id 去重
第 2 步  看正文关键词判断像不像抽奖（不发请求，很快）
           ↓  筛掉：没命中关键词、命中排除词、参与过了
第 3 步  判断还开不开着
        先从正文解析开奖时间；正文没写才退回看发布多久了
           ↓  筛掉：开奖时间已过、正文没写时间且发布太久
第 4 步  对剩下的挨个：关注 → 转发 → 评论
           ↓  每个动作之间随机等 20~45 秒
第 5 步  记进 record.json，打印结果报告
```

想改逻辑的话，`main.py` 从上往下分成 9 块，每块开头都有 `# 数字. 标题` 的注释，搜标题就能定位：

```
1. 配置          2. WBI 签名      3. 请求客户端
4. 参与记录      5. 找抽奖动态    6. 判断是不是抽奖
7. 三件套动作    8. 主流程        9. 命令行入口
```

```bash
schtasks /create /tn "bili-lottery" /tr "python \"C:\Claudcode\bilibili lottery\main.py\" --yes" /sc daily /st 10:00
```

不想要了就删掉：

